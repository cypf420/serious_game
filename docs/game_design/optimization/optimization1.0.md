## 一、文件定位与权威边界

本文件已经吸收《玩法全流程问题审计与技术解决方案》的问题、解决口径、当前实施状态、验收标准和剩余输入需求，作为后续内容与玩法优化的统一跟踪文档。

各文件的权威范围如下：

1. 《最终剧本》是人物、剧情、固定决策、硬结算和结局条件的内容权威。
2. 本文件记录已经确认的优化口径、当前技术闭环、剩余内容缺口和统一验收状态。
3. `code/backend/docs/01_玩法与行动/02_玩法全流程审计.md` 保留为审计取证与修复前缺陷依据；若其历史描述与本文件的当前状态冲突，以本文件更新时间更晚的状态表为准。
4. 本文件不是新的完整剧本，不能替代《最终剧本》。
5. 已确认条款必须同步进入新的不可变剧本包版本，不得覆盖既有已发布包。
6. 未经确认的政策数字、人物关系和剧情后果不得由开发人员或 LLM 猜测补写。

张立显式信任、D43 茶叶处置、玩家文本内容清洗和真实 Qwen 回放已经完成。当前新包仍保持 `draft`，是因为上述正式数字和人物规则尚未闭环，而不是因为玩家 feed 仍混有编剧批注。

## 三、统一的完整玩法循环

后续实现、试玩和验收统一使用以下循环：

```text
知道任务与手中资源
  -> 查看当日局势、人物、地点和已知材料
  -> 先处理当日固定事件与强制决策
  -> 选择自主行动或进入 NPC 多轮会谈
  -> 执行前看到行动点、直接财政支出、对象和程序条件
  -> 选择对象与必要参数
  -> 原子提交行动
  -> 获得不含隐藏数值的公开反馈、材料或后续入口
  -> 主动收工、行动点用尽或申请加班
  -> 夜间关系网进行幂等结算
  -> 次日显示不超过三行的晨间卡
  -> D90 冻结状态并按 14 条轴和表序首命中结局
```

必须同时坚持两项原则：

- 规则透明：行动点、直接财政支出、对象、程序门槛和不可用原因必须在提交前说明。
- 后果不透明：不得预告隐藏指标增减、人物信任数值、内部旗标、结局方向或实现说明。

## 四、已经确认的优化口径

### O-01 预算采用“基础授权、可安排余额、来源到账”分账

1. 基础授权总额为 8000 万元。
2. 前期协调费 200 万元已经实际支出，作为疑点挂账列示。
3. D1 可安排余额为 7800 万元。
4. 宏达化工 6000 万元是资金来源承诺，分期到账情况单独记录，不作为凭空新增预算。
5. 县级层面不能无来源自行突破 8000 万元。
6. 依法取得的上级专项拨款、追回款或责任企业追加赔偿，经相应审批后，可以形成有来源的预算调整。
7. 顶栏只显示玩家当前可安排余额；卷宗另列基础授权、已承诺、已支出、待审批、疑点挂账、资金来源与到账状态。
8. 当前版本主要约束预算授权和承诺，不增加独立的短期现金流断裂玩法。

统一数据口径：

```text
budget_base_authorized = 8000
budget_precoord_suspense = 200
budget_approved_adjustments = 0
budget_committed = 0
budget_paid = 200
budget_available = budget_base_authorized
                 + budget_approved_adjustments
                 - budget_committed
                 - budget_paid
```

### O-02 补偿采用“公式唯一账源、同一费用只入账一次”

1. P01–P15 按 36 户底表与当时生效的政策版本逐户测算。
2. 正式政策发布或方案获批后，相关金额进入预算承诺；实际签约或支付只改变承诺状态，不再次扣减可安排余额。
3. 剧情节点中的固定金额或金额区间必须声明费用性质：
   - 已包含在正式补偿中；
   - 标准外合法专案支出；
   - 行政或工程支出；
   - 私下加价等违规支出。
4. 同一费用不得同时通过逐户公式和剧情节点重复扣减。
5. 玩家执行前看到确定金额和公开构成，不从区间内随机取值。
6. 母稿金额区间只作为内容校准范围；正式执行金额由户表、政策、方案和审批结果确定。

### O-03 合法政策工具与违规选择分层保留

1. 差异化补偿只能基于经营、困难、医疗、住房、就业等客观资格及审批规则执行。
2. 提高整体补偿只能公开、统一调整，不能伪装成个别户私下加价。
3. 国企正式编制、无依据额外补偿、企业私下代付、先签后补等，不属于正常政策工具。
4. 上述违规行为仍可作为特定剧情中的玩家选择，不从玩法中删除；确认后由规则层写入事实、承诺和后续风险。
5. 角色 LLM 不得自行创造违规报价、岗位或硬结算。自由对话中出现政策外承诺时，只能提出一个待规则层确认的承诺候选。
6. 承诺确认文案统一为：

```text
额外保证：{玩家刚才提出的具体内容}
是否确定以这项保证换取签约？
```

7. 确认界面不提前显示廉政、巡察、攀比、反噬或指标后果。

### O-04 吸收 36 户基础数据，但不补造缺失明细

1. 吸收组长稿中的 36 个户号、户群归属、人口、住宅面积、宅基地面积、承包地总面积、经营面积、困难/医疗/就业标签和安置偏好。
2. 户群继续采用《最终剧本》锁定的 13 组，总计 36 户，签约按户群首触即锁。
3. 已登记总量为：户籍人口 122、实际常住 106、安置计人口 122、合法住宅 4745㎡、宅基地认定 5950㎡、超占 160㎡、承包地 82.8 亩、经营面积 45㎡。
4. 未提供的各地类面积、附属物数量、经营净收益、历史形成房面积、迁坟数量等统一标为待测量或待核验。
5. 后端和角色 LLM 不得自行猜测缺失数字。
6. 玩家通过查账、调档、走访、测量和医疗核验等行动，把项目从待核验变成已确认。
7. 未核验项目可以给出明确标注的估算范围，但不能形成正式报价、正式协议或最终支付。
8. 逐户动作只接受 `household_id`；普通玩家 DTO 不返回户群权重、签约锁及其他隐藏结算字段。
9. 如需完整自动回放，后续另补一份隐藏、确定且可校验的逐项明细表。

### O-05 晨间卡只主动出现一次，但看过后可以回查

1. 晨间卡只在对应日期清晨主动出现一次，不重复弹出。
2. 玩家看过的内容进入秘书记录或个人备忘，可在之后回看。
3. 回看记录必须标注信息性质：正式通知、已核实材料、未核实风声或 NPC 转述。
4. 回看不会把风声自动升级为事实、线索或证据。
5. 玩家尚未看过的隐藏内容不能从记录中补出。
6. D1–D89 每夜只结算一次，并生成一张不超过三行、不显示数值和旗标名的晨间卡。

### O-06 D75 采用“首批冻结、限定补签、D90 只读验收”

1. D75 不是全部协议的绝对截止日，而是首批有效协议、首批进度和首批奖励资格的冻结日。
2. D75 夜间先执行马长顺的从众自然触发，再冻结首批台账。
3. D75 同时生成实名未决名册，写明户群、户数上限、争议原因、承办人、前置路径和最迟办结日。
4. D76–D89 只允许处理 D75 已登记且由剧本指定节点触发的六类可能未决户群：老倔头 1 户、苗喜旺 1 户、宁德海 2 户、邓守本 1 户、何铁柱 4 户、周大山 4 或 6 户。
5. 马长顺不进入 D76 后白名单；他只能在 D75 夜间过从众阈值后进入首批台账。
6. 苗喜旺此前的旧纸属于附生效条件的预签文件，不是本期有效协议；第六章重新说明并由本人签署后，才首次入账。
7. 宁德海必须废止不合规代签材料、重新核验身份和授权，再由合法主体签署。
8. 何铁柱的医疗复检与救治是政府应履行的公共职责，不得与签约做违法交换；只有第五章已留下可核验未决路径、D75 已登记且 D86 本人真实签署时才入账。
9. 周大山 D86 补签只向第五章 DP5-09 选择 E、已取得「周大山肯等」的路径开放。选项 C、D 的寒心或拒谈不自动恢复。此前已预付 2 户则补 4 户，未预付则补 6 户。
10. D76–D89 的追加协议必须记录真实签署日，不得倒签为 D75，不享受首批奖励。
11. D90 只核验 D75 首批台账和 D76–D89 追加协议，不得新增、改签或补录。
12. 所有签约必须进入逐户群事件台账；聚合户数只是派生缓存，D90 聚合数与审计台账不一致时拒绝终局结算。

## 六、统一技术架构与运行契约

### 6.1 三类权威对象

1. `ConversationOpportunity`：人物、地点、开场、目标、知识边界和完成策略。
2. `ResourceActionDefinition`：资源/部门动作、对象 Schema、参数 Schema、成本、程序前置和完成处理器。
3. `ScriptedDecision`：固定剧情必须表态的 0 点节点，继续由规则层进行硬结算。

同一个剧情机会不得同时作为直接工具和会谈入口。

### 6.2 行动定义

每项工具至少包含：

```text
action_id
executor_kind
resource_ids
target_schema
parameter_schema
availability_rules
action_point_costs
budget_cost_formula
duration_policy
daily_cap / cooldown
legal_preconditions
completion_handler
result_contract
narrative_strategy
```

允许的 `executor_kind`：

- `conversation`
- `deterministic_analysis`
- `resource_dispatch`
- `policy_adjustment`
- `group_scene`
- `legal_procedure`

未知执行类型、找不到处理器或没有明确禁用原因的动作必须被剧本包发布校验拒绝。

### 6.3 行动 API 与报价

非会谈工具统一使用 `input_mode=resource_action`。提交结构至少包含：

```json
{
  "input_mode": "resource_action",
  "client_action_id": "客户端幂等键",
  "state_version": 42,
  "action_id": "third_party_water_test",
  "target_ids": ["loc_hongda_factory"],
  "parameters": {
    "sampling_point_id": "outlet_a",
    "lab_id": "independent_lab_1"
  },
  "quote_id": "quote_..."
}
```

执行前通过以下接口取得报价：

```text
POST /api/game/session/{session_id}/actions/quote
```

报价只返回玩家应当知道的内容：

- 当前实际行动点；
- 确定财政金额或公开计算明细；
- 占用时长、每日次数和承办资源；
- 法律、材料、地点前置及不可用原因；
- `quote_id` 及对应的 `state_version`。

报价不得返回隐藏指标 delta、信任数字、内部旗标或结局提示。执行时重新校验报价和状态版本；行动点、预算和硬状态必须同事务提交，失败时全部回滚。

### 6.4 处理器和 LLM 权限

`ActionHandlerRegistry` 要求每个动作满足以下至少一项：

- 有可达的通用执行入口；
- 有至少一个可达的剧情实例；
- 明确标记为当前版本禁用，且不在玩家案头宣称可用。

处理器只执行剧本包注册的硬结算。LLM 可以生成角色台词、合规软状态和候选披露，但不得决定预算、签约、事实、证据、内部旗标、固定决策和结局。

### 6.5 会谈完成策略

会谈统一支持：

```text
minimum_turns
completion_mode
required_disclosure_ids
required_goal_markers
complete_on_player_exit
complete_on_npc_exit
```

规则：

1. 玩家可以随时离场，但离场不等于任务完成。
2. 普通自由走访至少产生 1 个有效角色回合，才可记为已接触。
3. 强制教学会谈必须满足最低轮数及事实或目标要求，才开放后续剧情。
4. NPC 因越界送客时会谈可以结束，但不能自动发放正向完成事实。
5. 模型超时、客户端重试和同键重放不得重复扣行动点或重复生成完成效果。

### 6.6 信任、吐真和关系传播

1. 19 名深度 NPC 的信任由初值 40 加已开启旗标的注册影响派生，不允许 LLM 直接写入。
2. 同一旗标只结算一次；关闭旗标不倒扣；锁定后固定为 0。
3. 张立采用母稿专属显式结算，不套通用表；D31–D45 的决策、事件、自查落空和 D43 茶叶处置均已版本化登记，D45 后冻结。
4. 每轮会谈前计算有效信任，并应用疲惫、重复追问和越界行为修正。
5. 可披露集合为：人物自有知识 ∩ 当前剧情已存在事实 ∩ 信任档允许级别 ∩ 本章剩余额度。
6. 第四档的旗标级线索或实物证据，每人每章只能披露一次。
7. `will_share_with` 只形成经规则校验的传播候选，夜间再按注册关系边消费。
8. 普通玩家界面不显示 NPC 信任数值。
9. `disclosure_id` 表示本回合主要披露事实。对白同时涉及多个已授权事实时，服务端优先登记当前会谈目标事实；只有能够从白名单标记唯一确定时才补齐供应商漏填值，禁区事实仍直接拒绝。

### 6.7 日间、加班和夜间

1. D1–D89 每日先处理固定事件和强制决策，再开放自主行动。
2. 不因“45 分钟体验”自动跳过玩家白天。
3. `request_overtime(points=1|2|3)` 仅在基础额度用完、章内次数未满 3 且疲惫低于 75 时可用。
4. `end_day(active_rest=true)` 表示主动收工，剩余行动点作废并恢复疲惫。
5. 夜间读取当天动作日志、传播候选、关系边和人物状态，同一来源对同一对象只结算一次。
6. 没有固定事件的日期也必须提供晨间局势和可用行动入口。

### 6.8 内容分层与发布校验

母稿抽取必须区分：

- `player_narrative`
- `player_dialogue`
- `decision_prompt`
- `decision_option`
- `consequence_narrative`
- `designer_note`
- `code_rule`
- `ui_note`

只有前五类可以进入玩家 feed。发布校验至少拦截“开启旗标”“关闭旗标”“显示位”“本节点”“结局轴”“状态量”“代码照此算”等内部表达。

### 6.9 地图、知识与复盘

1. 地图使用玩家可见 `entry_cards`，展示名称、类型、对象、费用、锁定原因和提交所需内部 ID，但主文案不展示裸 ID。
2. 已掌握事实、线索和证据必须包含名称、正文、来源、核验状态及可理解的用途。
3. 复盘日志统一为：

```text
decision_resolved
action_started
action_completed
conversation_started
conversation_turn
conversation_ended
fact_learned
night_resolved
ending_resolved
```

4. 复盘展示人类可读名称、玩家选择、公开后果、行动点、公开预算支出和获得材料，不显示隐藏 delta、信任数值或内部旗标。
